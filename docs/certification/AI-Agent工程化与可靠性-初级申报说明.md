## 背景与业务场景

售前和解决方案工作中，经常需要根据客户招标参数确认长亭产品是否满足要求。传统做法依赖人工查产品参数表、翻历史材料、询问产品专家、登录演示环境截图，存在三个问题：

1. 参数核验耗时长，Excel 批量核验和逐条截图容易重复劳动。
2. 证据分散，口径容易只停留在“感觉支持”，缺少可审计来源。
3. 资料不足时容易过度承诺，后续投标或测试阶段存在风险。

ParaSure 的目标是把“参数识别、产品参数库检索、AI 工具规划、只读二次验证、证据包留存、结果矩阵输出”串成一个稳定可复用的 Agent 工作流，服务售前参数确认和客户测试支撑。

## 个人贡献

本人独立设计并实现 ParaSure 参数确认智能体，主要工作包括：

- 构建 CLI 入口，支持 `products`、`check`、`chat`、`web-test`、`doctor`、`evidence summary` 等命令。
- 接入 OpenAI 兼容 LLM，使 Agent 能够基于工具 schema 执行 plan/act/observe/evaluate 循环。
- 建立本地产品参数知识库，自动索引 `data/product_params/*.xlsx`，支持多种 Excel 表头结构。
- 设计确定性 fallback pipeline，在 LLM 不可用或批量处理时仍可生成符合性矩阵。
- 实现产品级上下文披露，只加载目标产品参数，避免一次性把全产品库暴露给 LLM。
- 实现只读 Web/API 二阶段验证，资料不足时由用户授权后再进入演示环境取证。
- 设计 Web 证据包：`screenshot.png`、`evidence.json`、`page_excerpt.txt`，用于复核和申报。
- 增加工具调用可观测性：记录 `duration_ms`、`error_type`、`retry_count`，便于分析失败和运行稳定性。
- 增加 `paramsure doctor` 和 `paramsure evidence summary`，用于交付前自检和脱敏证据统计。

## Agent 工程化设计

ParaSure 采用 Harness Engineering 思路：LLM 不直接“凭空判断”参数是否支持，而是在受控工具集合中选择动作。

核心链路如下：

1. `LLM Runtime`：负责规划、工具选择、观察整合和最终回答。
2. `ToolRegistry`：统一注册工具并封装工具调用结果，记录耗时、错误类型和重试字段。
3. `ParameterStore`：SQLite 本地知识库，保存长亭产品参数、来源文件、sheet 和行号。
4. `Retriever`：对客户参数和产品参数做检索匹配，产出候选证据。
5. `Decision`：按阈值区分“资料已满足 / 建议二次验证 / 需要二次验证”。
6. `WebVerifier`：通过 Playwright 和产品 playbook 做只读页面验证，产出证据包。
7. `Memory`：将用户输入、工具调用、观察和最终结论写入 `.paramsure/sessions/*.jsonl`。
8. `Excel Export`：输出符合性矩阵，包含结论、证据摘要、风险备注和建议应答口径。

## 可靠性与安全边界

ParaSure 面向售前参数确认，设计上优先避免误确认：

- 资料库匹配不足时不会直接输出“支持”，而是标记为“未确认”并建议二次验证。
- Web 验证必须同时具备关键词和页面上下文，只有关键词命中不判定为确认。
- Web 工具默认只读，阻止保存、删除、新增、提交、启用、禁用、发布、上传等风险动作。
- 二阶段 Web/API 验证需要用户确认并输入本次演示环境地址。
- 输出矩阵会保留风险备注，提醒正式投标前复核版本、型号、产品手册或专家口径。
- 通过 `doctor` 检查 Python、LLM 配置、产品参数目录、Playwright、Chrome CDP 和证据目录。
- 通过 `evidence summary` 汇总会话、工具观察、失败次数、证据包和截图数量，不输出敏感原文。

## 业务价值

ParaSure 能把售前参数确认从“人工查表 + 口头问询 + 手工截图”转为“可复现的 Agent 工作流”：

- 对少量参数，可直接自然语言询问目标产品是否支持。
- 对批量参数，可输入客户 Excel 并输出符合性矩阵。
- 对资料不足参数，可进入二阶段只读验证并保留截图和页面摘录。
- 对审核和复盘，可提供会话 JSONL、证据包和测试结果。
